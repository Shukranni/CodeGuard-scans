# Deploying CodeGuard on a free hosting platform

This project is **not a static website** — it is a React SPA plus a Django API
plus a background scan worker, and scans only progress while the worker runs.
Free hosting works, but you have to split it into pieces that free tiers
actually offer.

Everything in this repository is already configured for it.

---

## 1. What has to be hosted

| Piece | Tech | Free option used here |
| --- | --- | --- |
| Frontend (SPA) | React 18 + Vite | Render Static Site (free) — or Vercel / Netlify / Cloudflare Pages |
| API | Django 6 + DRF + JWT | Render web service (free plan) |
| **Scan worker** | `manage.py runscanworker` | runs **inside the API container** (`scripts/start_with_worker.sh`); in development the API also starts it on demand |
| Database | SQLite locally → **Postgres** in the cloud | Neon / Supabase / Aiven free Postgres |
| Uploaded project archives | local disk → **S3-compatible storage** | Cloudflare R2 / Backblaze B2 (free, strongly recommended) |
| Scanner binaries | `gitleaks`, `npm audit`, `semgrep` | `gitleaks` installed by the build script; `semgrep` installed best-effort with 512 MB guardrails (skipped cleanly if it does not fit) |

> **Why Postgres and object storage?**  Free hosts have an *ephemeral* disk:
> SQLite and `media/` are wiped on every deploy/restart. A hosted instance must
> put the database and the uploaded archives somewhere that survives.

## 2. The recommended setup: Render (both parts of one repo)

Render applies [`render.yaml`](render.yaml) as a **Blueprint** and creates two
services:

```
codeguard-api  (web service, free)  ── gunicorn  +  scan worker  (one container)
       ▲
       │  CORS + VITE_API_BASE_URL
       │
codeguard-web  (static site, free) ── React bundle on Render's CDN
```

### Step 0 — push the repository to GitHub

```bash
git init
git add -A
git commit -m "CodeGuard"
git remote add origin https://github.com/<you>/codeguard.git
git push -u origin main
```

`.gitignore` now excludes `*.zip` (the local `backend.zip` / `package.zip` /
`tailwind.config.zip` are ~1.6 GB each — **GitHub rejects files over 100 MB**,
so pushing them would fail), `node_modules`, `media/`, `db.sqlite3`, `staticfiles/`
and both `.env` files.

### Step 1 — create a free Postgres database

Any of these work and the URL format is the same:

| Provider | Free tier | Notes |
| --- | --- | --- |
| [Neon](https://neon.tech) | 0.5 GB | **Recommended** — no credit card, does not expire on a timer |
| [Supabase](https://supabase.com) | 500 MB | Pauses after ~7 days idle; click “Restore” to wake it |
| Render Postgres | 1 GB | **Expires after 30 days** — least suitable for this |

Copy the connection string, it looks like:

```
postgresql://user:password@host/dbname?sslmode=require
```

### Step 2 — apply the Render blueprint

1. Render dashboard → **New → Blueprint** → connect your GitHub repo → **Apply**.
2. Render reads `render.yaml` and creates `codeguard-api` and `codeguard-web`.
   The API build runs:
   ```
   bash scripts/install_gitleaks.sh
   pip install -r requirements-deploy.txt
   python manage.py collectstatic --noinput
   python manage.py migrate --noinput
   ```

### Step 3 — fill in the environment variables

Open **codeguard-api → Environment** and set these (`sync: false` in the
blueprint means “prompt me in the dashboard”):

| Variable | Required | Value |
| --- | --- | --- |
| `DATABASE_URL` | **yes** | the Postgres connection string from Step 1 |
| `DJANGO_SECRET_KEY` | auto | generated by Render (`generateValue: true`) |
| `DJANGO_DEBUG` | set | `False` |
| `DJANGO_ALLOWED_HOSTS` | set | `*` to start; ideally `codeguard-api-xxxx.onrender.com` |
| `DJANGO_CORS_ALLOWED_ORIGINS` | **yes** | `https://codeguard-web-xxxx.onrender.com` |
| `OPENROUTER_API_KEY` | optional | for the AI explanations (server-side only) |
| `AWS_STORAGE_BUCKET_NAME`<br>`AWS_ACCESS_KEY_ID`<br>`AWS_SECRET_ACCESS_KEY`<br>`AWS_S3_ENDPOINT_URL` | recommended | S3-compatible bucket for uploaded archives (see §4) |

Then open **codeguard-web → Environment** and set:

| Variable | Value |
| --- | --- |
| `VITE_API_BASE_URL` | `https://codeguard-api-xxxx.onrender.com` (full URL, no trailing slash) |

After changing it, run **codeguard-web → Manual Deploy → Clear build cache &
deploy** — Vite bakes the value into the bundle at build time.

### Step 4 — verify

| Check | How |
| --- | --- |
| API is up | `GET https://codeguard-api-xxxx.onrender.com/admin/login/` returns HTML (this is also Render's health check) |
| Workers running | Logs of `codeguard-api` start with `[codeguard] scan worker starting` |
| Migrations applied | No `relation "…" does not exist` errors |
| CORS | No `blocked by CORS policy` messages in the browser console |
| Scanners | `GET /api/scans/scanners/` (authenticated) — `gitleaks` and `dependency` should be `available: true` |
| End-to-end | Sign up → upload a ZIP → start a scan → results appear |

## 3. Alternative free platforms

### Frontend only (any of these)

The build output directory is `build` (set by `vite.config.mjs`), and the SPA
rewrite is provided in three places: `public/_redirects` (Render / Netlify /
Cloudflare Pages) and `vercel.json` (Vercel).

| Platform | Build command | Output dir | SPA rewrite |
| --- | --- | --- | --- |
| **Vercel** | `npm run build` | `build` (in `vercel.json`) | `vercel.json` rewrites |
| **Netlify** | `npm run build` | `build` (in `netlify.toml`) | `public/_redirects` |
| **Cloudflare Pages** | `npm run build` | `build` (set in the dashboard) | `public/_redirects` |
| **Render Static Site** | `npm install && npm run build` | `./build` (in `render.yaml`) | `routes` in `render.yaml` |

Whatever you choose, set `VITE_API_BASE_URL` to the deployed API URL and put
that frontend URL in the API's `DJANGO_CORS_ALLOWED_ORIGINS`.

### Backend only

| Platform | Free? | Verdict |
| --- | --- | --- |
| **Render** (web service) | yes | Best fit — `start_with_worker.sh` runs API + worker in one container |
| **Railway** | trial credit only | Works, but the trial runs out |
| **Fly.io** | trial (card required) | Works; needs a `fly.toml` |
| **Hugging Face Spaces** (CPU basic) | yes | 2 vCPU / 16 GB — the only free option that could realistically run **semgrep** |
| **PythonAnywhere** (free) | yes | ❌ No custom background processes → scans would stay `queued` forever |
| **AWS/GCP/Azure free tier** | mostly trial | ❌ Requires a credit card |

For any of them, the two non-negotiable requirements are:

1. a **run of the background worker** (a second process or a supervisor),
2. a **database that is not on the ephemeral disk** (`DATABASE_URL`).

## 4. Uploaded archives (object storage)

Scans re-read the uploaded ZIP (validation, extraction, source context for the
AI explanation). On an ephemeral disk those files vanish on redeploy — and the
S3/`local_archive_path` abstraction in `backend/projects/utils/archive.py`
is what keeps the app working either way.

Free buckets:

| Provider | Free storage | `AWS_S3_ENDPOINT_URL` |
| --- | --- | --- |
| [Cloudflare R2](https://developers.cloudflare.com/r2/) | 10 GB, no egress fees | `https://<account_id>.r2.cloudflarestorage.com` |
| [Backblaze B2](https://www.backblaze.com/cloud-storage) | 10 GB | `https://s3.<region>.backblazeb2.com` |

Set the four `AWS_*` variables on `codeguard-api` and redeploy. If you skip
this step the app still works until the API instance is restarted — at that
point previously uploaded archives are gone (new uploads keep working).

## 5. Known limitations of the free tier

| Limitation | Effect |
| --- | --- |
| Sleeps after 15 min without traffic | First request after idle takes **~1 minute** (cold start). Polling from the dashboard keeps it awake. |
| 750 instance hours/month | Roughly 31 days × 24 h of *running* time; spun-down hours are free. Exceeding it pauses the service until next month. |
| 512 MB RAM / 0.1 vCPU | Semgrep is installed **best-effort** at build time (a failed install never breaks the deploy) and runs with hard guardrails: `CODEGUARD_SEMGREP_JOBS=1` and `CODEGUARD_SEMGREP_MAX_MEMORY=192` (MiB). On a very large project it may skip files or report an error while `gitleaks` + `npm audit` still complete. |
| Ephemeral disk | Requires external Postgres (§2) and ideally object storage (§4). |
| One instance only | No scaling; long scans share CPU with HTTP requests. |
| `migration` runs in the build command | Fine for a single instance; move to `preDeployCommand` if you ever run more than one. |

Semgrep is installed automatically by the `render.yaml` build command as a
best-effort step (`pip install --no-cache-dir semgrep || echo …`): if it fits
on the instance it runs with small-host guardrails; if it does not, the build
still succeeds and scans report it as *skipped*. For heavy, always-on
semgrep at no cost, let GitHub run it for you instead — see §8.

## 6. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| “Starting the scan worker” | The worker is being started automatically — it takes a few seconds. If it stays visible, check the `codeguard-api` logs for `[codeguard] scan worker starting`. |
| Scans stay `queued` in production | The worker isn't running — check `codeguard-api` logs for `[codeguard] scan worker starting`. `CODEGUARD_AUTOSTART_WORKER` is off in production on purpose, so the dedicated worker process must be up. |
| Browser: `blocked by CORS policy` | Set `DJANGO_CORS_ALLOWED_ORIGINS` to the **frontend** origin (scheme + host, no trailing slash) and redeploy. |
| Refreshing `/dashboard` gives 404 | The SPA rewrite is missing — it lives in `public/_redirects` / `vercel.json` / the `routes` block of `render.yaml`. |
| `DisallowedHost` 500 | Set `DJANGO_ALLOWED_HOSTS` (a permissive `*` is the default). |
| `relation … does not exist` | `DATABASE_URL` points at a fresh database — the build runs `migrate`, so redeploy the API. |
| Scans stay `queued` and never finish | Worker not running, or the API and worker are in **different containers** (they must share one). |
| `gitleaks executable not found` | `bash scripts/install_gitleaks.sh` failed during build (GitHub rate limit) — rebuild; it falls back to a pinned release. |
| Scan finishes with *“Some scanners could not complete: semgrep”* | Semgrep ran out of time. The rule set is now cached locally (`backend/.semgrep_cache/`, refreshed weekly) so the download no longer eats the timeout, and the timeout scales with the project size. Tune with `CODEGUARD_SEMGREP_TIMEOUT`, `CODEGUARD_SEMGREP_SECONDS_PER_FILE` and `CODEGUARD_SEMGREP_MAX_TIMEOUT`; on a small machine use a lighter rule set (`CODEGUARD_SEMGREP_CONFIG=p/security-audit`). |
| Semgrep reports *“terminated unexpectedly (exit code 3221225786)”* | The process was killed, almost always because the machine ran out of memory. Give the container more RAM, set `CODEGUARD_SEMGREP_JOBS=1`, and cap the scanner with `CODEGUARD_SEMGREP_MAX_MEMORY=192`. |
| The first scan after a deploy is slow | The worker downloads the Semgrep rule set once on start-up (in the background). Every later scan uses the cached copy. |
| Login/register returns 500 | Usually `DATABASE_URL` invalid, or `DJANGO_SECRET_KEY` rotated between deployments (invalidates JWTs — sign in again). |
| Frontend calls `http://127.0.0.1:8000` | `VITE_API_BASE_URL` is empty on the static site — set it and **rebuild** (Vite inlines it at build time). |
| “Only repositories hosted on github.com can be scanned” | The URL was not a `github.com` repository URL — use the full form `https://github.com/owner/repository`. |
| “The repository … could not be downloaded” | The API container cannot reach `github.com`, or the repository is private and no token was supplied. Private repositories need a token with the `repo` scope (entered in the UI). |

## 8. Semgrep on GitHub Actions (free offload)

The 512 MB free instance can run Semgrep, but only just. Instead of
squeezing it onto the box, the scan worker can hand Semgrep to GitHub's CI
runners (2 cores / 7 GB of RAM) through the workflow committed at
`.github/workflows/semgrep-scan.yml`:

1. The worker signs a short-lived download link for the uploaded archive
   (`/api/scans/archive/?token=...`) and queues the workflow with
   `workflow_dispatch`.
2. The runner downloads the archive, installs Semgrep, scans, and uploads a
   `semgrep-output` artifact (JSON, kept for 1 day).
3. The worker polls the run, downloads the artifact and parses it with the
   same code path as a local run.

Every failure along that road (token expired, GitHub unreachable, workflow
missing) falls back to the local Semgrep if one is installed — enabling the
offload can never make a scan worse.

### Setup (all free, about 5 minutes)

1. **Create a token**: github.com -> Settings -> Developer settings ->
   Personal access tokens -> Tokens (classic) -> Generate new token.
   Scope: only **`repo`** — CodeGuard dispatches workflows and reads
   artifacts, it never modifies your repository. No billing setup is
   required — for a **public** repository Actions minutes are unlimited
   and free; a **private** repository gets 2,000 minutes/month on the
   GitHub Free plan (one scan uses roughly 1-3 minutes).
2. **Set three environment variables** on the `codeguard-api` service
   (Render dashboard -> Environment -> save; the service redeploys):

   | Variable | Value |
   | --- | --- |
   | `CODEGUARD_GITHUB_TOKEN` | the token from step 1 |
   | `CODEGUARD_GITHUB_ACTIONS_REPO` | `OWNER/REPO`, e.g. `Shukranni/CodeGuard-scans` |
   | `CODEGUARD_PUBLIC_API_BASE` | the public API URL without trailing slash, e.g. `https://codeguard-api-xqj2.onrender.com` |

   That is all — `render.yaml` already lists the three keys with
   `sync: false`.
3. **Verify**: run a scan and open the repository's Actions tab; the
   *CodeGuard Semgrep scan* run appears within seconds. `GET
   /api/scans/scanners/` then reports semgrep with the hint
   *Runs on GitHub Actions*.

The workflow file must sit **on the default branch** (`main`) — that is how
GitHub resolves `workflow_dispatch`.

### Optional knobs

| Variable | Default | Meaning |
| --- | --- | --- |
| `CODEGUARD_SEMGREP_CONFIG` | `p/default` | Registry config the runner uses (`p/security-audit`, `p/ci`, or an https URL). Local file paths stay on the worker, so they disable the offload. |
| `CODEGUARD_SEMGREP_REMOTE_JOBS` | `2` | Semgrep workers on the 2-core runner. |
| `CODEGUARD_SEMGREP_REMOTE_SLACK` | `300` | Extra seconds on top of the normal timeout for runner boot and install. |
| `CODEGUARD_ARCHIVE_TOKEN_MAX_AGE` | `900` | Lifespan of the signed archive link, in seconds. |
| `CODEGUARD_GITHUB_ACTIONS_WORKFLOW` | `semgrep-scan.yml` | Workflow file name. |
| `CODEGUARD_GITHUB_ACTIONS_REF` | `main` | Branch to dispatch against. |
| `CODEGUARD_GITHUB_POLL_SECONDS` | `5` | Polling interval while waiting for the run. |

### Privacy note (public repositories)

Workflow inputs are visible to anyone who can view the repository's Actions
runs — including the signed archive link. The link expires after
`CODEGUARD_ARCHIVE_TOKEN_MAX_AGE` (15 minutes by default) and grants access
to exactly one project archive while it is valid. If the scanned code itself
is sensitive, use a **private** repository instead: inputs stay hidden, and
the 2,000 free minutes still allow roughly 600-1,000 scans per month.

### If a scan reports that semgrep failed

| Symptom | Cause / fix |
| --- | --- |
| `Could not queue the Semgrep workflow: HTTP 404` | `CODEGUARD_GITHUB_ACTIONS_REPO` wrong, token lacks access, or `.github/workflows/semgrep-scan.yml` is not on `main`. |
| `HTTP 401/403` | Token expired or created without the `repo` scope. |
| `Timed out ... waiting for the Semgrep run` | Open the Actions tab — the run may be queued, or Actions may be disabled for the repository. |
| `produced no semgrep-output artifact` | The run failed before Semgrep finished — read the run's step logs. |
| `Invalid or expired archive link` in the run log | `CODEGUARD_PUBLIC_API_BASE` points at the wrong host or the link expired. The worker falls back to local semgrep automatically either way. |
| The `Set up Python` step fails with `No file in ... matched to [**/requirements.txt or **/pyproject.toml]` | `actions/setup-python` was given `cache: pip`, but the job never checks out the repository (the sources arrive as an archive), so there is no dependency file to hash. Leave the cache out — the workflow only runs `pip install semgrep`. |
